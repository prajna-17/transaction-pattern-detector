# Design Note

The application separates detection from explanation because the flag decision must be repeatable, testable, and auditable. `detector.py` validates the CSV, filters to credit transactions below the configured threshold, groups by account, sorts by timestamp, and identifies qualifying rolling windows. It uses `Decimal` for amounts and returns exact transaction-level evidence. The threshold comparisons are intentional: each individual amount must be strictly less than the reporting threshold, the combined amount must be strictly greater, and a transaction exactly on the configured time boundary is included.

`explainer.py` receives only `FlaggedAccount` evidence produced by the detector. Its request payload contains the account ID, evidence-window counts and boundaries, combined amounts, and the IDs, amounts, and timestamps of the included transactions. It does not receive the source CSV or configuration file, and its result retains the original deterministic account and evidence. The prompt tells the model to narrate supplied facts only; missing API keys, API failures, and malformed responses are represented as explanation errors while the deterministic evidence remains available.

The rapid pass-through detector is implemented separately in `pass_through_detector.py`. It processes credits FIFO, accumulates later unused debits within the configured inclusive window, and consumes debit evidence only after the configured outflow ratio is reached. It rejects duplicate transaction IDs and mixed timezone-aware/naive timestamps rather than making an unsafe assumption. `main.py` runs it after loading the same validated transactions and configuration.

The severity module is separate from detection but integrated into the CLI. It calculates a 0-100 score from existing structuring or pass-through evidence using Decimal arithmetic, clamps and rounds the result to two decimal places, and returns zero for missing or inconsistent evidence. The score combines configured evidence-strength factors such as transaction count, amount, outflow ratio, speed, and detector-condition consistency. It is a deterministic prioritization heuristic for analyst review, not a calibrated probability of fraud, and the LLM is never asked to assign or recalculate it.

The CLI displays both detector types, their exact evidence, and their deterministic scores. It then invokes separate LLM explanation paths downstream. The structuring path receives only structuring evidence; the pass-through path receives only pass-through evidence. If either LLM call fails or is rate-limited, the corresponding deterministic finding and score remain available.

A rejected alternative was to send the raw transaction list to the LLM and ask it to identify structuring before explaining the result. That would make detection dependent on probabilistic model behavior, allow unsupported calculations or assumptions, and violate the assignment's information boundary. The chosen design keeps the high-risk decision in small deterministic functions and limits the LLM to presentation. Groq's free OpenAI-compatible endpoint is called once per deterministic finding, which keeps the call volume proportional to the findings produced by the supplied dataset and avoids requests for accounts that were not flagged.
